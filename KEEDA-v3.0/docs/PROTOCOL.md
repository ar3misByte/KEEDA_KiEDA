# KiCad Live — WebSocket Protocol v1

Transport: a single WebSocket at `ws://<SERVER_IP>:8000/ws`.
Encoding: UTF-8 JSON, one JSON object per WebSocket text frame.

Every message has:

| Field | Type | Required | Meaning |
|---|---|---|---|
| `type` | string | yes | Message kind, from the table below |
| `ts` | float | no | Unix timestamp; the server stamps its own outbound messages |

The server **validates every inbound message** and replies with `error` rather
than closing the socket, unless the failure is fatal (bad `hello`).

## Identifiers

| Id | Format | Notes |
|---|---|---|
| `client_id` | 1–64 chars, `[A-Za-z0-9_-]` | Generated by the agent, stable across reconnects |
| `project_id` | 1–64 chars, `[A-Za-z0-9_.-]` | Must match between clients to share state |
| `uuid` | 1–64 chars, `[A-Za-z0-9-]` | KiCad object UUID |
| `user_name` | 1–48 chars, trimmed | Display only |

Anything failing these patterns is rejected with `error`. `project_id` is never
used to build a filesystem path without passing through the same validator plus
an explicit containment check.

## Message summary

| Type | Direction | Response |
|---|---|---|
| `hello` | client to server | `welcome` then `project_state` |
| `welcome` | server to client | — |
| `heartbeat` | both ways | `heartbeat` |
| `presence` | client to server | broadcast `presence_update` |
| `presence_update` | server to clients | — |
| `lock_request` | client to server | `lock_granted` or `lock_denied` |
| `lock_granted` | server to client | — |
| `lock_denied` | server to client | — |
| `lock_release` | client to server | broadcast `lock_update` |
| `lock_update` | server to clients | — |
| `change` | client to server | `change_ack` or `conflict`; broadcast `remote_change` |
| `change_ack` | server to client | — |
| `remote_change` | server to other clients | — |
| `conflict` | server to client | — |
| `conflict_resolve` | client to server | `change_ack` |
| `project_state` | server to client | — |
| `request_state` | client to server | `project_state` |
| `history` | server to client | — |
| `error` | server to client | — |
| `disconnect` | client to server | connection closed |

## 1. `hello` — client to server

First message on every connection. Sent again after a reconnect with the same
`client_id`.

```json
{
  "type": "hello",
  "client_id": "a3f1c0d2",
  "user_name": "Aditya",
  "project_id": "demo_board",
  "agent_version": "1.0.0"
}
```

Required: `client_id`, `user_name`, `project_id`. Optional: `agent_version`.

Response: `welcome`, immediately followed by `project_state`.

Errors: a malformed or missing `hello` closes the connection with code `4400`.
Sending a second `hello` on an already-registered connection is ignored with an
`error` of code `already_registered`.

## 2. `welcome` — server to client

```json
{
  "type": "welcome",
  "client_id": "a3f1c0d2",
  "project_id": "demo_board",
  "server_version": "1.0.0",
  "heartbeat_interval": 10,
  "client_count": 3
}
```

## 3. `heartbeat` — both directions

Client sends every `heartbeat_interval` seconds. The server replies with the
same type. A client that sends nothing for **30 s** is dropped and treated as a
disconnect (presence removed, locks released).

```json
{ "type": "heartbeat", "client_id": "a3f1c0d2" }
```

## 4. `presence` — client to server

```json
{
  "type": "presence",
  "client_id": "a3f1c0d2",
  "activity": "editing",
  "selection": ["R1"],
  "kicad_connected": true
}
```

`activity` is one of `idle`, `viewing`, `editing`, `routing`, `offline`.
`selection` is a list of references (display strings), max 32 entries.
Unknown `activity` values are coerced to `idle` rather than rejected.

Response: the server broadcasts `presence_update` to everyone in the project.

## 5. `presence_update` — server to clients

```json
{
  "type": "presence_update",
  "clients": [
    {"client_id": "a3f1c0d2", "user_name": "Aditya", "activity": "editing",
     "selection": ["R1"], "online": true, "kicad_connected": true},
    {"client_id": "b7e2", "user_name": "Rahul", "activity": "idle",
     "selection": [], "online": true, "kicad_connected": true}
  ]
}
```

## 6. `lock_request` — client to server

```json
{
  "type": "lock_request",
  "client_id": "a3f1c0d2",
  "uuid": "33c18730-0af9-4ad4-972d-782bf1b87199",
  "reference": "R1"
}
```

Response: `lock_granted` to the requester if the object is free **or already
held by the requester** (re-requesting your own lock refreshes its TTL and
always succeeds). Otherwise `lock_denied`.

A grant also broadcasts `lock_update` to everyone.

## 7. `lock_granted` — server to client

```json
{
  "type": "lock_granted",
  "uuid": "33c18730-...",
  "reference": "R1",
  "owner": "a3f1c0d2",
  "expires_in": 120
}
```

## 8. `lock_denied` — server to client

```json
{
  "type": "lock_denied",
  "uuid": "33c18730-...",
  "reference": "R1",
  "owner": "b7e2",
  "owner_name": "Rahul",
  "reason": "locked_by_other"
}
```

On receiving this the agent must **not** send changes for that object, and
should revert the object locally to the server's authoritative value.

## 9. `lock_release` — client to server

```json
{
  "type": "lock_release",
  "client_id": "a3f1c0d2",
  "uuid": "33c18730-..."
}
```

Omitting `uuid` releases **all** locks held by that client. Releasing a lock the
client does not own is a no-op (not an error) — this keeps reconnect logic
simple. Response: broadcast `lock_update`.

## 10. `lock_update` — server to clients

```json
{
  "type": "lock_update",
  "locks": [
    {"uuid": "33c18730-...", "reference": "R1", "owner": "a3f1c0d2",
     "owner_name": "Aditya", "expires_in": 118}
  ]
}
```

Always the **complete** lock table, not a delta. Clients replace their view
wholesale, so a dropped message cannot desynchronise the lock display.

## 11. `change` — client to server

The core message. One or more field-level changes, each carrying the version the
client believed the object was at.

```json
{
  "type": "change",
  "client_id": "a3f1c0d2",
  "change_id": "a3f1c0d2-17",
  "changes": [
    {
      "operation": "modify",
      "object_type": "footprint",
      "uuid": "33c18730-...",
      "reference": "R1",
      "field": "position",
      "base_version": 7,
      "old": {"x": 60.0, "y": 50.0},
      "new": {"x": 65.0, "y": 50.0}
    }
  ]
}
```

`operation` is `add`, `modify` or `remove`. `field` is required for `modify`.
Supported fields: `position`, `rotation`, `layer`, `value`, `reference`.
`change_id` must be unique per client; a repeat is treated as a duplicate and
acknowledged without re-applying (idempotent retry).

Response: `change_ack` if every change was accepted, or `conflict` listing the
ones that were not. **Partial acceptance is possible**: accepted changes are
applied and broadcast, rejected ones are reported.

## 12. `change_ack` — server to client

```json
{
  "type": "change_ack",
  "change_id": "a3f1c0d2-17",
  "accepted": [{"uuid": "33c18730-...", "field": "position", "version": 8}],
  "rejected": []
}
```

## 13. `remote_change` — server to other clients

Broadcast to every client in the project **except** the originator.

```json
{
  "type": "remote_change",
  "origin_client_id": "a3f1c0d2",
  "origin_user_name": "Aditya",
  "changes": [
    {
      "operation": "modify",
      "object_type": "footprint",
      "uuid": "33c18730-...",
      "reference": "R1",
      "field": "position",
      "new": {"x": 65.0, "y": 50.0},
      "version": 8
    }
  ]
}
```

The receiving agent marks each `uuid` as echo-suppressed, updates its baseline to
`new`, then applies the change to KiCad. It must **not** rebroadcast.

## 14. `conflict` — server to client

```json
{
  "type": "conflict",
  "change_id": "b7e2-9",
  "conflicts": [
    {
      "uuid": "33c18730-...",
      "reference": "R1",
      "field": "position",
      "your_base_version": 7,
      "current_version": 8,
      "your_value": {"x": 60.0, "y": 55.0},
      "server_value": {"x": 65.0, "y": 50.0},
      "conflicting_user": "Aditya"
    }
  ]
}
```

The agent surfaces this to the user and, by default, reverts the object to
`server_value` so the two KiCad instances do not silently diverge. Nothing is
merged automatically.

## 15. `conflict_resolve` — client to server

Sent when a user explicitly chooses to overwrite. This is the *only* way to win
a conflict, and it is always a deliberate human act.

```json
{
  "type": "conflict_resolve",
  "client_id": "b7e2",
  "change_id": "b7e2-9",
  "resolution": "keep_mine",
  "uuid": "33c18730-...",
  "field": "position",
  "value": {"x": 60.0, "y": 55.0}
}
```

`resolution` is `keep_mine` or `keep_theirs`. `keep_theirs` is a no-op
acknowledgement. `keep_mine` force-bumps the version and broadcasts.

## 16. `project_state` — server to client

Full authoritative snapshot. Sent after `hello` and on `request_state`.

```json
{
  "type": "project_state",
  "project_id": "demo_board",
  "version": 42,
  "objects": {
    "33c18730-...": {
      "uuid": "33c18730-...", "reference": "R1", "object_type": "footprint",
      "position": {"x": 65.0, "y": 50.0}, "rotation": 0.0,
      "layer": "F.Cu", "value": "10k", "version": 8
    }
  },
  "locks": [],
  "clients": []
}
```

If the server has no state yet for this project, the **first client to send a
`hello` seeds it** from its own board, via a `change` message containing `add`
operations. This is how an empty server bootstraps without ever reading a file.

## 17. `request_state` — client to server

```json
{ "type": "request_state", "client_id": "a3f1c0d2" }
```

## 18. `history` — server to client

Sent on `request_history`, and pushed to dashboards after each accepted change.

```json
{
  "type": "history",
  "entries": [
    {"version": 8, "ts": 1758200551.4, "user_name": "Aditya",
     "reference": "R1", "field": "position", "summary": "moved R1",
     "old": {"x": 60.0, "y": 50.0}, "new": {"x": 65.0, "y": 50.0}}
  ]
}
```

## 19. `error` — server to client

```json
{
  "type": "error",
  "code": "invalid_message",
  "message": "field 'uuid' failed validation",
  "context": {"type": "lock_request"}
}
```

Codes: `invalid_message`, `unknown_type`, `not_registered`,
`already_registered`, `invalid_id`, `rate_limited`, `internal_error`.

An `error` never closes the connection except for a failed `hello`.

## 20. `disconnect` — client to server

Optional politeness message before closing. The server treats an abrupt socket
close identically, so this is never required for correctness.

```json
{ "type": "disconnect", "client_id": "a3f1c0d2" }
```

## Connection lifecycle

```text
CLIENT                          SERVER
  |-- TCP/WS connect ------------->|
  |-- hello ---------------------->|
  |<-- welcome --------------------|
  |<-- project_state --------------|
  |<-- presence_update (broadcast)-|
  |                                |
  |-- heartbeat (every 10s) ------>|
  |<-- heartbeat ------------------|
  |                                |
  |-- presence ------------------->|--> broadcast presence_update
  |-- lock_request --------------->|
  |<-- lock_granted ---------------|--> broadcast lock_update
  |-- change --------------------->|
  |<-- change_ack -----------------|--> broadcast remote_change to others
  |                                |
  |-- (socket closes) ------------>| release locks, drop presence,
  |                                |  broadcast presence_update + lock_update
```

## Error behaviour summary

| Situation | Server behaviour |
|---|---|
| Non-JSON frame | `error` / `invalid_message`, connection kept |
| Unknown `type` | `error` / `unknown_type`, connection kept |
| Message before `hello` | `error` / `not_registered`, connection kept |
| Bad `hello` | close with code `4400` |
| Id fails pattern | `error` / `invalid_id`, message dropped |
| More than 200 messages/sec from one client | `error` / `rate_limited`, message dropped |
| Unhandled server exception | `error` / `internal_error`, logged, connection kept |
